## 2. Разделение состояния

| Тип                 | Что хранит                                                                             | Где                                             |
| ------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------- |
| **Server state**    | товары, аналитика, категории                                                           | TanStack Query                                  |
| **URL state**       | поиск, фильтры, сортировка, страница, размер страницы, период аналитики                | search params роутера (валидируются Zod-схемой) |
| **Client/UI state** | выбранные строки (`Set<id>` / режим «все по фильтру»), открытые модалки, sidebar, тема | Zustand / локальный state                       |
| **Form state**      | значения и ошибки редактора                                                            | библиотека форм                                 |

Правила:

- Серверные данные **не копируются** в Zustand.
- Selection хранит только id (и флаг «выбраны все результаты фильтра» + исключения), не объекты товаров.
- Источник правды для фильтров — URL; компоненты читают их через типизированный хук `useProductsFilters()`.

## 4. Query keys и кэш

Фабрика ключей на фичу:

```ts
export const productKeys = {
	all: ['products'] as const,
	lists: () => [...productKeys.all, 'list'] as const,
	list: (filters: ProductsFilters) =>
		[...productKeys.lists(), filters] as const,
	details: () => [...productKeys.all, 'detail'] as const,
	detail: (id: string) => [...productKeys.details(), id] as const,
}

export const analyticsKeys = {
	all: ['analytics'] as const,
	summary: (f: AnalyticsFilters) =>
		[...analyticsKeys.all, 'summary', f] as const,
	sales: (f: AnalyticsFilters) => [...analyticsKeys.all, 'sales', f] as const,
}
```

Политики:

- `placeholderData: keepPreviousData` для списка и графика — без «мигания» при смене страницы/фильтров.
- `staleTime` списка — десятки секунд; справочников (категории) — большой.
- Prefetch следующей страницы списка; prefetch детали товара по hover на строку (опционально).
- Фильтры в ключе — **нормализованный** объект (стабильный порядок, без `undefined`), чтобы не плодить дубли кэша.

## 5. Мутации

| Операция                      | Стратегия                                                                                                                              |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Изменение товара (редактор)   | pessimistic: ждём ответ → обновляем `detail`, инвалидируем `lists`                                                                     |
| Bulk: цена / остаток / статус | **optimistic**: `onMutate` → cancel queries → snapshot → patch всех кэшированных списков → `onError` rollback → `onSettled` invalidate |
| Архивирование                 | optimistic + undo-окно ~5 сек (откладываем реальный запрос или шлём компенсирующий)                                                    |

Нюансы, которые нужно решить и записать в decisions:

- Как патчить кэш, если товар лежит в нескольких кэшированных списках с разными фильтрами (и после патча может перестать подходить под фильтр).
- Что делать при частичном успехе bulk-операции (mock API должен уметь возвращать `{succeeded, failed}`).
- Обработка гонок: повторная мутация поверх незавершённой, отмена исходящих запросов.
- Идемпотентность и повтор «только для неудачных».

## 6. Mock API

Эндпоинты (MSW):

- `GET /api/products` — `q, category, status, stock, sort, page, size` → `{items, total}`
- `GET /api/products/:id`
- `PATCH /api/products/:id` — валидация, 400/409/500 по условию
- `POST /api/products/bulk` — `{ids | filter, action, payload}` → `{succeeded, failed}`
- `GET /api/categories`
- `GET /api/analytics/summary` — выручка, заказы, средний чек, конверсия + дельта
- `GET /api/analytics/sales` — временной ряд по группировке

Требования:

- Данные генерируются детерминированно (seed) — для воспроизводимых замеров.
- Задержка 200–800 мс, настраиваемый процент ошибок (для тестов rollback и error-состояний).
- Хранилище в памяти: мутации реально меняют данные, повторный GET видит изменения.
- Серверная фильтрация/сортировка/пагинация реализованы в моках, как в настоящем API.

## 7. Performance Challenge

### 7.1 Версия «до» (намеренно наивная)

- Все 10–50k записей в одном массиве, клиентская фильтрация/сортировка, все строки в DOM.
- Выбор строки ререндерит всю таблицу; нет мемоизации.

### 7.2 Измерения

Фиксируем до оптимизации и после (на одних и тех же данных, seed одинаковый):

- время первого рендера таблицы;
- время реакции на ввод в поиск;
- время выбора строки / «выбрать все»;
- количество DOM-узлов;
- число и длительность ререндеров (React Profiler);
- потребление памяти (heap snapshot);
- FPS при скролле.

Результаты — в `perf-report.md`: таблица «метрика / до / после / во сколько раз», скриншоты профайлера.

### 7.3 Кандидаты на оптимизацию (выбор — после профилирования, не заранее)

- серверная пагинация и фильтрация;
- виртуализация строк (TanStack Virtual), фиксированная высота строки;
- `React.memo` для строк, стабильные колбэки, селекторы Zustand;
- selection как `Set<id>` вне данных таблицы, подписка строки только на свой флаг;
- debounce поиска, `useDeferredValue` / `startTransition` для тяжёлых обновлений;
- вынос тяжёлой работы (сортировка/фильтрация) в Web Worker — только если замеры покажут необходимость;
- code splitting страницы Analytics и графиков.

### 7.4 Сравнение до/после

Переключатель реализации через `?table=naive|optimized` (только в dev) + мини-панель с метриками рендера.

## 8. Обработка ошибок

- Глобальный `ErrorBoundary` на уровне страницы + локальные на независимые блоки (каждая KPI-карточка, график).
- Единый слой нормализации ошибок API (`ApiError` с кодом, сообщением, field errors).
- Retry: для GET — автоматически 1–2 раза с backoff, для мутаций — только вручную.
- Серверные ошибки валидации маппятся на поля формы.

## 9. Структура проекта

```
src/
  app/            # router, providers (QueryClientProvider), layout
  features/
    products/
      components/ # ProductsToolbar, ProductsTable, ProductRow, BulkActionBar, ProductEditor
      api/        # fetchers, useProducts, useUpdateProduct, useBulkUpdate, query keys
      model/      # filters schema (Zod), selection store, cache patch helpers
    analytics/
      components/ # AnalyticsFilters, KpiCard, SalesChart
      api/
  shared/
    ui/           # ErrorBlock, EmptyBlock, PageHeader
    lib/          # форматтеры, useDebounce, apiClient, ApiError
    mocks/        # MSW handlers, генератор данных
```

Правила: фичи не импортируют друг друга напрямую; `shared` не знает о фичах; запросы к API — только через слой `api/`, компоненты работают с хуками.

## 10. Этапы реализации

1. **Каркас**: Vite + TS, Tailwind v4, HeroUI v3, роутинг, layout, тема.
2. **Mock API**: генератор данных, MSW, эндпоинты списка и деталей.
3. **Products v1 (naive)**: таблица, поиск, фильтры, сортировка, пагинация; URL-состояние.
4. **Selection + Bulk UI**: выбор строк, панель действий (пока без оптимизма).
5. **Product Editor**: форма, валидация, ошибки API, обновление кэша.
6. **Mutations**: bulk-операции, optimistic update + rollback, undo для архивирования.
7. **Analytics**: фильтры в URL, KPI, график, независимые состояния.
8. **Замеры «до»**: профилирование на 10k / 50k, фиксация метрик.
9. **Оптимизация** по результатам профилирования, итеративно (одно изменение → замер).
10. **Замеры «после»**, `perf-report.md`, `decisions.md`, финальная чистка.

## 11. Чек-лист готовности

- [ ] Серверный и клиентский state разделены; нет дублирования серверных данных в сторе
- [ ] Query keys организованы через фабрики, инвалидация предсказуема
- [ ] Фильтры, сортировка, страница восстанавливаются из URL
- [ ] Optimistic update откатывается корректно (проверено принудительной ошибкой мока)
- [ ] Частичный успех bulk-операции обработан
- [ ] Аналитика: смена фильтров обновляет несколько блоков, ошибки изолированы
- [ ] Есть воспроизводимые замеры «до/после» и отчёт
- [ ] Каждое ключевое решение объяснимо и записано в `decisions.md`
